# Threadline 如何落实《质性研究入门指南》的分析原则

更新日期：2026 年 10 月 2 日。第一阶段提交：`eded412`；第二阶段 R4–R7 的增量见第 7 节，具体提交版本以 Git 历史为准。

Threadline 的使用方式是：**提交已有文稿 → Agent 完成一次分析 → 输出一份报告**。它借鉴《质性研究入门指南》中有关材料整理、编码、备忘录、反例、解释边界和报告写作的原则，辅助研究者检查分析依据。

本文中的“符合”指这些原则在本项目中的具体落实程度，不表示工具完成了全书所描述的研究过程，也不表示模型报告已经通过学术意义上的可信度检验。

## 2. 书中原则与当前实现的对应

| 书中原则 | 项目如何落实 | 落实程度与边界 |
|---|---|---|
| 7.1、7.3.2：围绕研究目的理解材料，避免预设类别强加于数据 | 研究问题与关注点进入编码、主题和评估指令；要求没有对应材料时保持未知 | 提供分析方向；模型仍可能误解材料，需要研究者核对 |
| 7.3.1、7.3.2：编码连接具体材料及其意义 | 编码保存逐字摘录、来源编号、字符位置和相邻语境；只有经过原文校验的编码参与后续分析 | 程序可以检查摘录是否存在；不能仅凭存在就证明编码解释恰当 |
| 7.3.3：反复整理编码、明确定义，防止定义漂移 | 保留编码编号、归并关系、定义及包含和排除边界、定义历史；生成可读编码簿 | 支持整理和追踪；不会自动保证分类方案适合研究问题 |
| 7.3.2、7.3.4、7.7.1：回到材料，比较差异，寻找遗漏与反例 | 首次候选主题后，默认对本次全文逐片回查一次；发现有效新证据后补码并更新候选主题 | 支持一次材料复查；不等于书中先通读再编码的完整顺序，也不保证穷尽全部遗漏 |
| 7.2.1：用备忘录记录分析思考和不确定性 | 保存编码及主题备忘录、归类理由、反证和未决问题；私人手记与模型输入隔离 | 模型理由可供检查；不能替代研究者随时写下的思考和自反 |
| 7.3.4、7.6：超越话题清单，建立编码与主题之间的联系 | 主题引用有效编码，区分模式、反例、证据缺口与候选解释；生成候选故事线 | 提供可追溯的分析草稿；有编号不意味着主题意义已经成立 |
| 7.7.1、7.7.2：检查解释依据，交代边界和局限 | 保留反例与回查记录；复核清单分为原文与来源核对、矛盾与反例检查、解释边界 | 支持材料内部核对；未实施成员核查、同行评审或外部审计 |
| 第 5 章、8.1：交代研究者立场，反思如何形成解释 | 保留研究者自反记录和报告中的人工诠释位置；私人记录不自动发送给模型 | 提供记录位置；自反的内容和判断由研究者完成 |
| 7.6、8.4、8.6：引文与分析及诠释相联系，避免引文堆砌 | 网页、文本和 Word 报告提供原文引证、分析理由、反例、未知及已保存的研究者诠释；引文去重并设置预算 | 支持报告草稿；选取短摘录不等于完成厚描，模板和预算也不能保证写作质量 |
| 7.7.1、附录 B：整理并保留分析过程资料 | 完整 JSON 保存原文、编码、回查、评分、修订与人工改动事件；可选择保存阶段文件 | 保留本次分析关键节点；不覆盖完整研究、田野或全部人工思考过程 |

## 3. 第一阶段三项改造如何对应这些原则

### 3.1 范围对齐：分析本次文稿，说明材料边界

书中 7.7.2 要求说明研究包括什么、没有包括什么及其原因。结合你确定的使用方式，本项目将分析范围限定为本次提交的已有材料。这个范围是用户要求，不是书中规定所有质性研究只能处理一份文稿。

网页保留粘贴文本、单个 TXT/DOCX 上传、研究问题、来源信息和两种分析模式。每次启动独立结果，清理绑定上次结果的界面状态；生成、评估与修订可以在任务内部多次处理，最终仍输出本次任务的一份报告。

原来的“下一轮可以收集什么”调整为“当前材料复核”：核对原文与来源、检查矛盾与反例、说明解释边界。材料没有回答的问题作为未知保留。模型指令限制的是新生成的任务建议，原文中的采访对话照常作为分析材料。

旧 `next_data_plan` 字段和历史抽样记录保留兼容；历史收集记录不进入模型或默认报告。旧 Python 接续接口仍可使用，本版网页不提供接续入口。

实现依据：[界面与任务状态](../streamlit_app.py)、[模型指令](../src/prompts.py)、[复核清单](../src/next_data_plan.py)、[研究记录兼容结构](../src/research_records.py)。

### 3.2 证据限制：先确认原话存在，再讨论它意味着什么

书中 7.3 将编码视为整理与连接数据的过程，7.7 要求检查诠释依据。本项目据此增加统一的原文证据限制。**“摘录存在于文稿中”与“这件事在现实中已被证实”分别记录。**

| 状态字段 | 回答的问题 | 对分析的影响 |
|---|---|---|
| `evidence_status` | 这段摘录及其字符位置能否在实际输入原文中匹配？ | 只有已匹配记录可作为编码和主题的支持证据 |
| `verification_status` | 当前材料对所述事情提供了什么核实依据？ | 保留陈述性质及核实限度；仅有受访者陈述也可以分析 |

`evidence_status` 区分已匹配、缺少摘录、匹配失败、尚未核验。实际校验按来源找到原文，并检查 `text[source_start:source_end] == excerpt`。导入数据自称“已匹配”不能代替这一步；缺少可回查原文的旧摘录保持尚未核验。

例如，文稿确实写着“我觉得平台忽略了我的反馈”。即使没有平台记录印证，仍可以分析“受访者感到反馈被忽略”。这个摘录本身不能证明“平台确实忽略了反馈”，也不能证明造成忽略的原因。

未通过校验的条目保留编号、名称和失败原因，供查看及导出。归并家族展开、按名称补找编号、类别映射、主题生成、评估和修订采用同一限制，避免无效条目通过其他入口成为支持证据。缺乏有效支持的候选发现降为证据缺口，不能通过评估。

全文回查后仍没有有效编码时，返回可保存的结果，平均分为空，显示“无有效证据、未评分”，跳过评估与修订。不会把没有依据的结果用低分或高分包装成已完成的分析。

实现依据：[原文与主题引用校验](../src/evidence.py) 中的 `validate_evidence`、`matched_codes`、`link_themes_to_codes`；[生成](../src/agents/generation_agent.py)、[评估](../src/agents/evaluation_agent.py)、[修订](../src/agents/refinement_agent.py)。

### 3.3 全文回查：让候选主题接受材料中的反例检查

书中 7.3.2 强调阅读全部数据，7.3.3 强调修订编码方案后回到材料，7.3.4 强调比较以及未被说明的内容，7.7.1 强调检查解释。本项目将这些原则落实为本次任务中的一次自动回查：

**读取原文 → 初次编码与候选主题 → 全文回查一次 → 校验新增证据 → 必要时更新候选主题 → 评估与修订 → 一份报告。**

回查按已有自然边界切块，每次请求提供候选主题摘要、当前片段和该片已有有效编码，检查遗漏支持、反例和解释条件。即使初次没有有效编码，也执行回查。

回查发现先经过逐字及位置校验。新增有效证据追加编号，已有编号保留；重复证据复用已有编号。发现新增有效证据时，重新整合编码簿、进行映射并更新候选主题，再进入原有评估流程。全文回查只执行一次。

回查状态、完成片段数量、失败片段、新增编号和发现理由保存到 `corpus_review`。未被最终主题采用的反证仍保留在回查记录中。部分请求失败时保留已完成结果，显示“回查部分完成”或“回查失败”，整体结果不能通过；取消任务正常终止。

“回查完成”只说明所有计划片段完成了本次请求和解析，不能证明模型找到了所有反例或解释限制。模型可能在两次阅读中重复相同的偏差，研究者仍需检查候选解释。

实现依据：[流程编排](../src/tama.py) 的 `run_analysis`、[全文回查](../src/agents/generation_agent.py) 的 `review_corpus`、[回查提示词](../src/prompts.py) 的 `build_corpus_review_prompt`。

## 4. 保存与报告如何支持回到材料

完整结果的 `source_documents` 保存本次规范化原文、来源编号与 SHA-256。文本按与编码一致的方式去掉首尾空白，字符位置以保存后的文本为准；TXT/DOCX 输入对应读取后的文字，不是 Word 页码或原文件字节位置。校验值用于检查保存内容的一致性，不能证明文稿的现实真实性。

选择本地保存或下载完整 JSON 时包含原文；Word 报告呈现选取的有效引文、分析理由和复核信息，不附整篇原稿。关闭本地结果和阶段文件保存时，不创建结果目录，本次数据只在当前服务进程中保留。

结果中的模型分数用于检查候选主题的覆盖度、模式性、区分度和相关性。它不等于书中的成员检查、理论三角验证、同行评审或外部审计。来源字段也只记录出处，不代表已经做过多来源互证。报告“通过”表示达到本次程序的评估与回查要求，不表示研究结论已被证明，更不表示理论饱和。

实现依据：[结果保存](../src/tama.py)、[报告结构与引文筛选](../src/reporting.py)、[网页展示与下载](../streamlit_app.py)。

## 6. 当前仍需研究者完成的部分

- 判断编码是否恰当、主题是否有研究意义，核对短摘录所依赖的完整语境。
- 结合研究目的、理论、经验及其他可用材料形成诠释，考虑替代解释，并写出适用边界。
- 完成自反思考、成员核查、同行讨论等适合本研究的工作；生成、评估、修订三个模型角色不等同于三个独立研究者的交叉验证。
- 判断资料是否足够、是否达到某种方法要求；一次回查完成、分数达标和没有新增编码都不足以宣布饱和。

当前仍没有新增批量上传或跨任务比较；第二阶段已增加本次比较矩阵、人工诠释保存及分析关键节点记录。这些增量不等于完整研究审计，也不能替代研究者思考。

第 7 章 7.5 讨论的软件以辅助整理与检索为主，本项目进一步使用模型生成编码和候选主题，这是技术扩展，不是书中提出的自动化方法。研究者仍承担材料理解、诠释与研究结论的判断责任。

## 7. 第二阶段：后四项建议的落实

| 建议及书内依据 | 当前实现 | 核查代码 |
|---|---|---|
| R4 比较矩阵；7.2.3、7.4、7.6 | 按本次证据已有的参与者、案例、说话人标签、事件、资料时间或材料分组；每格区分支持、反对、混合、未涉及，并可回到对应原文。研究者可确认分组并记录依据 | [矩阵与计数](../src/evidence_views.py)、[比较界面](../src/review_ui.py) |

| R6 语境阅读；7.5、7.6 | 根据实际全文和位置展开所属问答或段落；明确提问与回答的关系。报告可选附精选引文语境，长语境列相关片段并提示网页可展开。没有原稿时只显示已保存附近语境 | [原文语境](../src/evidence_views.py)、[报告](../src/reporting.py) |
| R7 解释复核与过程记录；5.3、7.7、7.8 | 两种解释分别挂支持、反证、边界和未解释问题，记录采用、保留或否决的理由。研究者复核状态独立于模型评分；修改已复核的记录后回到待复核。原稿、编码定义、回查、评估、主题修订及人工改动留痕 | [记录与事件](../src/analysis_records.py)、[编排](../src/tama.py)、[评估](../src/agents/evaluation_agent.py)、[复核界面](../src/review_ui.py) |

“未涉及”是没有关联的有效编码，不是证明原稿完全没有涉及某话题，更不是反对或刻意沉默。矩阵分别计数有效编码、不同原文位置、材料、已标记参与者及案例；同一人三份材料仍是一个参与者，说话人标签不能自动推断其身份。

本阶段的人工记录不增加模型调用。私人手记、自反记录、报告诠释和解释复核记录分别处理，研究者写字或保存不意味着已提交模型。恢复报告也不会接续模型分析，JSON 中的原保存路径不会获得写入权限；开始新分析仍只使用新提交文稿。

原文回查已经主动检查遗漏支持和反证，本阶段进一步将独立反例、信息断点及证据缺口保留为复核发现，不按共享模式评分，也不交给模式修订删除。只有这些发现时未评分；有有效模式时，评分通过与研究者是否复核仍分别显示。证据缺口继续阻止整体通过。

`audit_trail` 保留本次关键流程节点；人工事件保存改动前后内容及理由，报告可查看研究者为何缩小或改变解释。事件顺序是程序记录的节点顺序，不是每一次模型请求的完整时间线；旧版缺失事件不会被补造。原稿校验值变化时，旧复核状态失效。

验证见 [第二阶段测试](../tests/test_second_phase.py)：包含矩阵的混合与未涉及、同人多份材料计数、重复证据、未知身份、完整长问答、诠释保存与主题重排、JSON 与 Word 输出、原稿变更、两种解释与分组校正、低频反例保护及停止后的未评分状态。验收结果与文件清单见 [第二阶段改造记录](../第二阶段改造记录.md)。
