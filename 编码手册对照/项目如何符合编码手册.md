# 当前项目如何符合《质性研究编码手册》

这份说明对照《质性研究编码手册》第 2 版的提炼稿和当前项目。读完可以决定：已经合上的保持不动，还没合上的要不要做。

提炼稿在 `/Users/chriss/Downloads/质性研究/质性研究编码手册-提炼`。下面说的「手册」都指这份提炼。

## 手册要的顺序

手册把编码看成一轮一轮的工作。对当前这种访谈分析，有用的是这六步。

1. 方法宜少。没有把握时从很少的几种起步，不合适再换。一次用很多种，会把材料搅浑。
2. 第一轮的代码是临时的。名称可以是过程短语，也可以直接用受访者的原话。定义、什么算、什么不算，等到编码放在一起比较之后再写。
3. 编码的时候就写备忘录，挂在相关编码上，标上日期。先把想法写下，不必先分成固定类型。没有备忘录，代码只是标签。
4. 第一轮之后先做映射，再谈主题。四步都要留下：全部编码，收成类别，再收成更少的类别，然后写成概念。概念不是理论。另做一张全景：看得出每条编码底下有多少材料，但条数不等于重要。
5. 主题是这一轮编码之后的解释，不是把类别名称再抄一遍。编码到这里应该变少。变少靠合并真正同义的，不靠删掉出现得少的。
6. 收尾由人来做。只留下最要紧的三个，写一句论断，同时找出支持它的材料和不支持它的材料。报告里写明这次用了什么编码方法。

项目里的顺序是：抽码、同义归并、代码映射、编码备忘录、全景，然后才归纳主题。见 `src/agents/generation_agent.py` 的 `run`。主题生成之后还有评分和修订（`src/tama.py`）。那一步修订的是主题，不是把编码再编一遍。

## 已经合上的

| 手册的要求 | 项目现在的做法 | 落在哪里 |
|---|---|---|
| 方法宜少；行动用过程短语，原话另标 | 默认只有过程编码和实境编码 | 抽码提示词；`in_vivo` 为真时方法写成实境编码 |
| 第一轮先临时，比较后再写定义 | 第一轮只留名称和逐字原文。定义、包含、排除在同义归并时才写，并写明什么情况不算 | `build_code_extraction_prompt` 不收定义；`build_code_merge_prompt`、`semantic_merge` |
| 编码贴着原话，不贴概括句 | 摘录必须逐字相同。对不上就清空，并写入待核查 | `generate_codes_from_chunk` |
| 切分不要把谈话切成孤立的单元 | 切块落在问答、段落、说话人或句末 | `src/chunking.py` |
| 编码时写备忘录，标日期，不先规定类型 | 归并和映射时可以写一句，挂上编码编号。没有想法就留空。研究者补在标记里的话不进模型 | `04_code_memos.md`；`code_memos_for_model` |
| 备忘录可以再用来形成类别 | 这些备忘录会进入主题提示词 | `build_theme_generation_prompt` |
| 编码本要有定义、何时用、何时不用、例子、相关代码、备注 | 方法、定义、包含、排除、正例、相关编码、备注、并入来源。非典型例和「似是而非」不要求模型填 | `05_codebook.md`；`Code.method`、`related_code_ids`、`note` |
| 映射四步都要留档 | 第 1 步由程序列出全部规范编码。后三步用模型。编造的编号丢掉；没被提到的编码单独留下。映射失败时保持全集，分析不中断 | `06_code_map.md`；`map_codes`、`build_code_map` |
| 全景只供查看，条数不等于重要 | 数字是逐字摘录的段数。按类别排，不按这个数字排。评分也不用它 | `07_code_landscape.md`；`render_code_landscape` |
| 主题在映射之后，类别名不是主题 | 主题记下它落在哪些多编码类别里。类别名按编码编号回填，不直接采用模型另起的类名 | `attach_category_names` |
| 同义才合并，出现得少的不因此删除 | 仅同一来源、同一位置和语境的重复证据自动去重；同名不同材料先保留独立，再比较意义。旧编号留在 `merged_from` | `exact_merge`、`semantic_merge` |
| 定义变化后回到旧摘录核对 | 定义前后版本与理由留档，关联摘录标为需复核；研究者可记录适用或不适用，不自动删除旧证据 | `definition_history`、`definition_review`、定义复核表单 |
| 情境标记用于查找与比较 | 来源、资料类型、参与者、时间、场景和事件按实际资料填写；代码另保留明确说话人标签与相邻语境 | `SourceMetadata`、`Code.source`、`Code.speaker`、`Code.context` |
| 讲原因只是启发式 | 必须引用具体编码，不能写成已经证实的原因 | 主题类型 `candidate_mechanism` |
| 反面情况留下来 | 反例单独成栏。修订主题时不能为了整齐删掉 | 主题的反例编码 |
| 报告写明用了什么编码方法 | 过程编码、实境编码、同义归并、代码映射、主题归纳 | `reporting.py` 的 `CODING_METHODS_NOTE` |
| 收尾由人聚焦 | 主题聚焦栏由研究者填写，三个位置只是可调整的写作提示；整体论断可关联支持和反证。模型故事线保持草稿状态 | `reporting.py` 的 `_focus_lines`、整体论证表单 |
| 什么让我惊讶、着迷、干扰 | 记在本机，不进模型 | `reflexivity.md` |

一次分析还会写下 `04_memos.md`（主题备忘录，与编码备忘录分开）、`00_summary.txt` 和 Word 报告。界面里故事线同样标成草稿，编码簿能看到方法、相关编码和备注（`streamlit_app.py`）。

有意收窄的地方：映射第 1 步不交给模型重列，避免漏掉编码。第 2 步若没有把编码放在一起，后三步就按全集重复，并写明「没有进一步归类」。备忘录的 11 类思考不是必填。聚焦栏不用条数或分数替人挑选那三个主题。

## 还没合上的

这些是手册里有、这个项目还没有的做法。要不要做，取决于后面的材料。

- 全库开编之前，先拿一两页试编，由人决定方法是否合适。
- 同一份材料内部细分多个时间、场景或事件的精细标记；目前支持资料级标记及编码级说话人标签。
- 按研究问题把大段标成索引，方便以后细看。索引不是发现。
- 同一段原话除了做法，还可以再标价值观、情绪或对立。只在问题确实涉及这些时加，一次仍然只用很少几种。
- 自动重抽全部旧材料仍未实现。当前已支持定义历史和逐条旧摘录复核，完整重读或重新抽码由研究者按需进行。
- 参与者讲到「因为……所以……」时，可以写成前因、中介、结果。这仍是启发式，不能写成已经证实的原因。现在的原因说明还是一整段。
- 记录物品、场景和文件时，允许用名词作描述编码。行动仍用过程短语。

## 不搬进默认流程的

手册是一部方法备查，不是要求一次用完。下面这些不进入当前项目的默认分析：

拟剧、母题、叙事、言语交流、协议编码、文化素材主题分类目录、领域和分类法、给摘录打强度分、自动写出中心类别或理论、用编码者一致率决定合格与否。没有前一项研究时不做精细编码。材料没有时间顺序时不做纵向矩阵。主轴编码的整套步骤也不作为每轮必经之路。
